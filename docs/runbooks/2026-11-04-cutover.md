## Deviations from the plan

### 1. Migration failed on 1970-dated rows

The first run of
`db/migrations/2026_08_08_add_observation_time_submission_time.sql` stopped at the
backfill (step 2):

```
ERROR 1292 (22007): Incorrect datetime value: '1970-01-01 00:00:00'
for column `observation_time` at row 238701
```

`TIMESTAMP` can't hold anything earlier than `1970-01-01 00:00:01` UTC. One or more
rows were dated `1970-01-01` at hour 0, period 0: reports from clients whose clock had
never been set. Step 1 (add columns) had already committed, because DDL can't be rolled
back. The backfill rolled back, and nothing after it ran.

**Recovery:** reloaded the dump (resetting the table), then ran
`DELETE FROM satellite WHERE day < '1970-01-02'` (**14 rows**, 731,180 → 731,166),
then re-ran the full migration. It succeeded: 0 NULL `observation_time`, 0 historical
rows with `submission_time`, both indexes built. The deleted rows still exist on dallas190
and in the cutover dump. This is the same treatment as the future-dated rows under #23.

**Why CI didn't catch it:** the `migration-dry-run` job's sample data had no
pre-1970 row. Both the script (new step 0) and the CI sample data have been updated
since, so the repo matches what ran.

### 2. PHP containers had no php.ini (hotfix #51)

The first real report on status.amsat.org saved correctly, but the page showed a
`Deprecated: Creation of dynamic property CallSignParser::$callSign` notice and a
`headers already sent` warning. The `php:*-apache` image ships no `php.ini`, so
`display_errors` was on and `output_buffering` off. The second meant `submit.php`'s
`setcookie()` silently failed, so the form stopped remembering callsigns.
dallas190's Ubuntu PHP used production settings, which is why neither showed there.
Fixed by #51 (`php.ini-production` in both images). The underlying code issues are
tracked separately.

### 3. #30 contained more than the runbook described

Six commits landed on #30 after the runbook was written and shipped with it:
corrections (the grid and summary count each callsign's latest report per cell or
block), and POST `/reports.php` returning a boolean `correction` in place of
`replaced_count`. That also closed #31. The CHANGELOG entry for #30 describes them.
The runbook's breaking-change wording ("`replaced_count` removed", "repeat reports no
longer replaced") predates them. The CHANGELOG is authoritative.

### 4. #49 rebase

#49 was stacked on #30's branch. A first rebase attempt that diffed against the
then-current #30 branch would have reverted the six commits above. It was caught before
pushing, and #49 was rebuilt from its own two commits on top of `main`.

## Lessons for next time

- **Dry-run migrations against a full copy of production data**, not just CI sample
  data. The rehearsal in section A would have caught the 1970 rows before the window.
- **A migration script should either be safe to re-run or say plainly that it isn't.**
  Here, step 1 committing before step 2 failed meant a plain re-run failed with
  "duplicate column". The recovery was to reload the dump.
- **Check the PHP configuration of a new container image**, not just the code.
- **Re-read a PR's full commit list right before merging**, especially a long-lived
  one, so the runbook and announcements match what actually ships.
